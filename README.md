# Изменения хранения данных: WAL-персистентность и REVERT без snapshot-копий

Этот документ описывает, что было изменено в исходном проекте, чтобы
выполнить два требования задания:

1. *"Все данные должны храниться в файловой системе. Потеря данных
   недопустима."*
2. *"Реализация [REVERT] через полное копирование (snapshot) файлов БД
   запрещена."*

Изменены только `include/storage.hpp`, `include/executor.hpp` (точечно),
`include/logger.hpp`, `src/server.cpp`, `src/client.cpp`, `CMakeLists.txt`.
Файлы `btree.hpp`, `parser.hpp`, `string_pool.hpp`, `types.hpp`, `script.txt`
не изменялись.

---

## 1. Что было не так в исходной версии

- Вся база данных целиком хранилась в оперативной памяти
  (`std::map<db, std::map<table, std::vector<Row>>>`).
- При каждом `INSERT`/`UPDATE`/`DELETE` файл таблицы (`table.bin`)
  **полностью перезаписывался** с нуля (`save_table()` открывала файл с
  `std::ios::trunc` и писала весь вектор строк заново). Диск был просто
  периодическим дампом содержимого RAM, а не независимым источником истины.
- `REVERT` был реализован через каталог `snapshots/<table>/<timestamp>.snap`
  — полную копию всех строк таблицы на каждый чекпоинт. Это прямое
  нарушение требования "снэпшот-копирование запрещено", и вдобавок такие
  копии дублируют данные записей (что противоречит и другому требованию —
  "дублирование данных записей для построения индексов запрещено", хоть и
  сформулированному про индексы, тот же принцип применим и здесь).

## 2. Новая модель: Write-Ahead Log (WAL)

Каждая таблица хранится на диске в виде **одного add-only журнала операций**
`<table>.wal`. Каждая мутирующая операция дописывается в конец файла как
самостоятельная, помеченная временем запись:

| Тип записи   | Когда создаётся                        | Что содержит                          |
|--------------|------------------------------------------|----------------------------------------|
| `INSERT_ROW` | `INSERT INTO ...`                        | индекс новой строки + её значения      |
| `UPDATE_ROW` | `UPDATE ... SET ...`                     | индекс изменённой строки + новые значения |
| `DELETE_ROW` | `DELETE FROM ...`                        | индекс удалённой строки (tombstone)    |
| `COMPACT`    | создание таблицы, компакция, REVERT      | полное текущее состояние строк на этот момент |

Формат записи в файле:

```
[size_t len][timestamp chars][1 байт: тип операции][payload...]
```

Запись **дописывается** (`std::ios::app`) и сразу `flush()`-ится. Байты уже
записанных ранее операций никогда не трогаются — если процесс упадёт
посреди записи новой операции, всё, что было подтверждено раньше, остаётся
целым на диске.

### Загрузка = replay журнала

При старте (`StorageManager::load_all()` → `load_table()`) состояние таблицы
**не читается как готовый дамп**, а вычисляется заново: файл `.wal`
прочитывается с начала, и каждая запись применяется по очереди
(`replay_wal()`):

- `INSERT_ROW` — добавляет/устанавливает строку по её индексу;
- `UPDATE_ROW` — заменяет строку по индексу;
- `DELETE_ROW` — помечает строку как удалённую (tombstone);
- `COMPACT` — заменяет весь текущий набор строк переданным состоянием.

В памяти таблица — это *материализованное представление*, кэш для быстрого
выполнения запросов, но не источник истины: источник истины — журнал на
диске.

### Устойчивость к сбоям

Если последняя запись в файле оказалась не дописана до конца (сбой питания,
`kill -9` и т.п.), `replay_wal()` останавливается на первой повреждённой
записи, выводит предупреждение и возвращает всё, что успело быть корректно
прочитано. Программа не падает и не теряет уже подтверждённые данные —
теряется, в худшем случае, только последняя незавершённая операция, которая
и так не была подтверждена клиенту.

Это было проверено тестом: файл `.wal` намеренно обрезался на несколько
байт (имитация обрыва записи), после чего программа успешно перезапускалась
и восстанавливала все строки, записанные до обрыва.

### Компакция журнала (не snapshot)

Журнал, который никогда не усекается, рос бы бесконечно. Поэтому после
накопления `COMPACTION_THRESHOLD` (500) записей журнал **компактируется**:

1. Текущее материализованное состояние таблицы записывается как **одна**
   запись `COMPACT` во временный файл `<table>.wal.compact.tmp`.
2. Временный файл атомарно переименовывается (`std::filesystem::rename`) на
   место старого `<table>.wal`.

Атомарность `rename()` гарантирует, что в любой момент на диске лежит
*либо* полностью целый старый журнал, *либо* полностью целый новый —
никогда нет промежуточного, наполовину записанного файла таблицы.

**Важно, почему это не нарушает запрет на snapshot-копирование:** компакция
журнала — это стандартная и общепринятая техника логирования (то же самое
делают WAL/redo-логи промышленных СУБД, Raft-логи, LSM-деревья), она **не
создаёт исторических точек восстановления путём копирования файлов БД**, а
лишь укорачивает уже прожитую историю до одного эквивалентного состояния.
`REVERT` по-прежнему работает через replay, просто не может откатиться к
моменту *раньше* последней компакции — точно так же, как в реальных
СУБД глубина отката ограничена сохранённой историей журнала.

Проверено тестом: 600 последовательных `INSERT` были сжаты в один
`COMPACT`-record, после перезапуска все 600 строк читаются корректно.

## 3. REVERT — исключительно через replay, без копий файлов БД

Старая сигнатура публичного API (`revert_to_snapshot`, `revert_all_tables`)
сохранена, чтобы `parser.hpp` и синтаксис команды `REVERT` не менялись —
поменялась только реализация внутри `storage.hpp`:

```cpp
void revert_to_snapshot(const std::string& table_name,
                         const std::chrono::system_clock::time_point& timestamp) {
    // Пересчитываем состояние с нуля из журнала, беря только записи
    // с timestamp <= заданный момент времени.
    auto rows = replay_wal(current_db_, table_name, /*use_cutoff=*/true, timestamp);
    data_[current_db_][table_name] = rows;

    // Сам факт отката тоже фиксируется в журнале как обычная запись
    // COMPACT — журнал остаётся единственным линейным логом операций.
    WalRecord rec;
    rec.op = WalOp::COMPACT;
    rec.compact_rows = rows;
    append_wal_record(current_db_, table_name, rec);
}
```

Ни в одной из веток кода `REVERT` не происходит копирования файла таблицы —
только чтение существующего журнала и один `append` в конце.

Проверено тестом: после `INSERT` новой строки и последующего
`REVERT users <метка_времени_до_вставки>;` строка исчезает из результата
`SELECT`, при этом в каталоге БД не появляется ни одного файла `.snap` или
любой другой копии — только продолжающий расти файл `users.wal`.

## 4. Что осталось прежним

- Формат сериализации отдельных значений (`Value`/`Row`) — тот же
  побайтовый формат, что и в оригинале (тип-тег + данные), не менялся.
- Схема таблицы (`<table>_schema.bin`) по-прежнему хранится отдельным
  небольшим файлом, целиком перезаписываемым при `CREATE TABLE` — это
  метаданные, а не данные записей, и требование про запрет snapshot-копий
  к ним не относится (схема меняется крайне редко, полноценная история
  версий схемы не требуется заданием).
- B-tree индексы (`btree.hpp`) не были персистентны и в оригинале, и такими
  и остались: они не хранят копию данных (только индекс → номер строки),
  строятся в памяти при старте и после каждой структурной операции — это
  соответствует требованию *"дублирование данных записей для построения
  индексов запрещено"*.

## 5. Побочно исправленные ошибки оригинала

**a) Индексы не восстанавливались после перезапуска.** При перезапуске
процесса B-tree индексы для колонок с модификатором `INDEXED` не
восстанавливались, из-за чего `INSERT` в уже существующую (загруженную с
диска) таблицу приводил к разыменованию пустого `unique_ptr` и падению
программы. Добавлено восстановление индексов при старте `Executor` из уже
загруженных на этом этапе данных таблиц (`Executor::Executor()` в
`executor.hpp`).

**b) Segfault на агрегатных запросах (`SUM`/`AVG`/`COUNT`).** Запрос вида
`SELECT SUM(age) FROM users;` приводил к падению сервера. Причина: парсер
для агрегатной функции кладёт имя колонки (`age`) не в `select_columns`, а
в отдельное поле `aggregate_col`, поэтому `execute_select()` строил для
каждой строки **пустой** `result_row` (цикл по `select_columns`, который в
этом случае пуст). Дальше `apply_aggregate()` пытался прочитать
`row.values[col_idx]` из этого пустого вектора — обращение за границы
массива, неопределённое поведение → segmentation fault (в отличие от
обычных ошибок валидации, такое падение не перехватывается `catch
(std::exception&)` в `server.cpp` и роняет весь процесс сервера, а с ним и
все активные подключения других клиентов).

Исправление: для агрегатных запросов `execute_select()` теперь сохраняет
**полную** строку таблицы (как и для `SELECT *`), чтобы `apply_aggregate()`
могло взять из неё значение нужной колонки по индексу. Дополнительно в
`apply_aggregate()` добавлена проверка границ (`col_idx >= row.values.size()`)
как защитный барьер на будущее. Проверено тестом на
`SUM`/`COUNT`/`AVG`, в том числе в сочетании с `WHERE`.

## 6. Кроссплатформенность (macOS/Linux/Windows)

Дополнительно к требованиям про хранение, сетевой слой `server.cpp` /
`client.cpp` был переведён с Windows-специфичного Winsock (`winsock2.h`,
`closesocket`, `SOCKET`, `WSAStartup`) на переносимый код: BSD sockets
(`sys/socket.h`, `netinet/in.h`, `arpa/inet.h`, `unistd.h`, `close()`) под
`#else`-веткой того же `#ifdef _WIN32`, так что один и тот же исходник
собирается и на macOS/Linux, и на Windows. Аналогично `logger.hpp`
(`localtime_s` → `localtime_r`/`localtime_s` по платформе) и
`CMakeLists.txt` (замена MinGW-специфичных флагов на `find_package(Threads)`).

## 7. Как запустить и протестировать программу

### 7.1. Требования

- Компилятор с поддержкой C++17: `g++`/`clang++` на macOS/Linux, MSVC/MinGW
  на Windows.
- `cmake` версии 3.14+.
- Интернет-доступ при первой сборке (CMake сам скачает `nlohmann/json` через
  `FetchContent` — руками ставить ничего не нужно).

### 7.2. Сборка

macOS / Linux:

```bash
cd dbms-main            # корень проекта, где лежит CMakeLists.txt
mkdir build && cd build
cmake ..
cmake --build . -j
```

После сборки в `build/` появятся два исполняемых файла: `server` и `client`.

Windows (MinGW или MSVC, из "Developer Command Prompt"):

```bat
cd dbms-main
mkdir build && cd build
cmake -G "Visual Studio 17 2022" ..
cmake --build . --config Release
```

### 7.3. Запуск сервера

```bash
./server                  # порт 8080, лог access.log (значения по умолчанию)
./server 9090              # свой порт
./server 9090 my_access.log   # свой порт и файл лога
```

Сервер печатает в консоль количество загруженных при старте баз данных и
таблиц (это как раз тот самый replay WAL-журналов с диска) и остаётся
запущенным, ожидая подключений. Каталог `./data` рядом с исполняемым файлом
сервера — это и есть файловая система хранения (создаётся автоматически при
первом запуске).

Остановить сервер: `Ctrl+C`, либо нажать Enter в его консоли (сервер
специально ждёт Enter после старта — так задумано в исходном коде).

### 7.4. Запуск клиента

Клиент — отдельный процесс, подключается к серверу по TCP. Запускать нужно
**в другом терминале**, пока сервер работает.

Интерактивный режим:

```bash
./client                       # подключение к 127.0.0.1:8080
./client -h 127.0.0.1 -p 9090   # свой адрес и порт
```

```
dbms> CREATE DATABASE shop;
dbms> USE shop;
dbms> CREATE TABLE goods (id INT INDEXED, name STRING NOT_NULL, price INT);
dbms> INSERT INTO goods (id, name, price) VALUE (1, "Bread", 50), (2, "Milk", 80);
dbms> SELECT * FROM goods;
dbms> exit;
```

Команда обязательно должна заканчиваться `;` — только тогда она отправляется
на сервер (можно писать её в несколько строк).

Пакетный режим (из готового файла со скриптом на SQL-подобном языке):

```bash
./client script.txt                    # к 127.0.0.1:8080
./client -h 127.0.0.1 -p 9090 script.txt
```

В проекте уже есть готовый `script.txt` с демонстрацией всех базовых
операций (`CREATE`, `INSERT`, `SELECT`, `SELECT ... WHERE`, `BETWEEN`,
`LIKE`, `UPDATE`, `DELETE`, агрегаты `COUNT`/`SUM`/`AVG`) — им удобно
проверить, что сборка в принципе работает.

### 7.5. Проверка требования "хранение в файловой системе, потеря данных недопустима"

1. Выполнить через клиента несколько `INSERT`/`UPDATE`/`DELETE` (как в
   примере выше).
2. Убедиться, что каталог `./data` рядом с сервером не пуст и содержит по
   таблице подкаталог/файлы:
   ```bash
   find ./data -type f
   # data/shop/goods.wal
   # data/shop/goods_schema.bin
   ```
3. **Остановить сервер жёстко**, как при реальном сбое (не через Enter, а
   так, будто он упал):
   ```bash
   pkill -9 -f "./server"
   ```
4. Снова запустить `./server` на том же порту и через клиента выполнить
   `SELECT * FROM goods;` (после `USE shop;`) — все ранее вставленные и
   изменённые данные должны быть на месте. Это подтверждает, что данные
   лежат на диске, а не только в оперативной памяти процесса.

### 7.6. Проверка требования "REVERT не через копирование файлов БД"

1. Записать текущее время в формате `yyyy.mm.dd-hh:mm:ss.msmsms` (можно
   просто посмотреть часы, секунды точно совпадать не обязаны — достаточно
   момента до следующей вставки).
2. Выполнить ещё один `INSERT` после этого момента.
3. Выполнить `REVERT goods yyyy.mm.dd-hh:mm:ss.msmsms;` (подставив
   зафиксированное время) — новая строка должна пропасть из
   `SELECT * FROM goods;`.
4. Убедиться, что при этом в `./data/shop/` **не появилось** ни каталога
   `snapshots/`, ни файлов с расширением `.snap` — есть только продолжающий
   расти `goods.wal`:
   ```bash
   find ./data/shop -type f
   ```

### 7.7. Автоматизированные проверки (без сети, напрямую по коду)

В процессе разработки состояние проверялось тремя отдельными тестами,
которые компилируются напрямую против `include/storage.hpp` и
`include/executor.hpp`, без поднятия сервера/клиента по сети (это упрощает
CI и локальную проверку логики):

- **Персистентность через "перезапуск"** — создаётся `Executor`, делаются
  `INSERT`/`UPDATE`/`DELETE`, затем **создаётся новый** `Executor` (эмуляция
  перезапуска процесса) и проверяется, что все изменения читаются из
  журнала на диске; дополнительно проверяется, что на диске нет ни одного
  файла `.snap`.
- **Компакция журнала** — вставляется 600+ строк (выше порога компакции в
  500 записей), проверяется, что журнал сжался в одну запись, и что после
  повторной загрузки все 600 строк на месте.
- **Устойчивость к обрыву записи** — файл `.wal` намеренно обрезается на
  несколько байт (имитация сбоя питания/`kill -9` посреди записи), после
  чего проверяется, что программа не падает и восстанавливает все
  полностью записанные до обрыва строки.

Скомпилировать и запустить такие тесты можно самостоятельно, написав
`main()`, который создаёт `dbms::Executor` и напрямую вызывает
`.execute("...")` с нужными запросами, например:

```cpp
#include "executor.hpp"
#include <cassert>
#include <iostream>

int main() {
    dbms::Executor exec;
    exec.execute("CREATE DATABASE t;");
    exec.execute("USE t;");
    exec.execute("CREATE TABLE x (id INT INDEXED, v STRING);");
    exec.execute("INSERT INTO x (id, v) VALUE (1, \"a\");");
    auto r = exec.execute("SELECT * FROM x;");
    std::cout << r.to_json() << std::endl;
}
```

```bash
g++ -std=c++17 -Iinclude -pthread test.cpp -o test \
    $(pkg-config --cflags nlohmann_json 2>/dev/null)
./test
```

(если `nlohmann_json` не установлен системно, проще всего собрать полный
проект через CMake — он сам подтянет заголовок — и подключить путь к нему
через `-I`).
